# RP-410A Search Dynamics Findings

**Status:** v1.1 — revised per scientific review  
**Telemetry source:** `/tmp/rp410_telemetry` (baseline campaign, seed 42)  
**Instances:** 20 benchmark instances (setA-01 through setA-20)  
**Note:** Operator fingerprints are not yet available — operator tagging was found to be
non-functional in the baseline campaign (all moves recorded as "initial"). A corrected
campaign must be run before operator-level conclusions can be drawn.

---

## 1. Primary Finding: Peak Improvements Were Never Observed

Across the entire baseline campaign:

- **132 accepted improvements**
- **356 total generations**
- **20 benchmark instances**

the zone classifier recorded **zero Peak-classified moves**.

| Zone       | Count | Fraction |
|------------|-------|----------|
| Peak       | 0     | 0.0%     |
| Shoulder   | 31    | 23.5%    |
| Transition | 29    | 22.0%    |
| Tail       | 38    | 28.8%    |
| Mixed      | 33    | 25.0%    |
| Neutral    | 1     | 0.8%     |

This is an empirical observation, not a hypothesis. The zone classifier defines Peak as
rank-1 arc saturation (the single most-loaded arc). No accepted improvement in this
dataset was classified as a Peak-only improvement.

**What this does not prove:** The telemetry cannot distinguish whether Peak improvements
are absent because they are never generated by the operators, because they are generated
but not retained by selection, or because the objective function masks them. All three
explanations are consistent with the data. Distinguishing them requires RP-408
(lexicographic evaluation) and operator-level analysis once fingerprinting is working.

**What this does prove:** Under the current scalar objective, the evolutionary search
accepted no move that was classified as a Peak-only improvement across 132 accepted
improvements and 20 instances. This is a structural property of the search trajectory,
not a claim about the objective function's theoretical properties.

---

## 2. Zone Distribution Is Approximately Balanced (Excluding Peak)

Ignoring Mixed moves, the remaining zone counts are:

```
Shoulder    31  (23.5%)
Transition  29  (22.0%)
Tail        38  (28.8%)
```

These are approximately equal. The search is not Tail-dominated. The anomaly is not
that Tail improvements are over-represented — it is that **Peak is completely absent**.

This reframes the research question: the question is not "why does the search prefer
Tail?" but "why is Peak disconnected from the evolutionary search?"

---

## 3. Mixed Moves Differ Between Instance Groups

Mixed moves (improvements that span multiple zones simultaneously) account for:

- **Collapsed Basin instances:** 43.9% of accepted improvements
- **Shape Competition instances:** 16.5% of accepted improvements

This difference is large enough to be worth investigating. It suggests the search
dynamics differ substantially between the two groups. Whether the cause is network
topology, operator behaviour, evaluation structure, or something else cannot be
concluded from this data alone.

**Caution on the "Collapsed Basin" classification:** The instances labelled as
collapsed-basin here (setA-02, setA-04 through setA-08) were classified based on
RP-406C lexicographic analysis. If RP-410A uses a different criterion, this should be
made explicit to avoid inconsistency between reports.

---

## 4. Generation Count Varies Dramatically Across Instances

| Instance | Generations |
|----------|-------------|
| setA-01  | 62          |
| setA-03  | 92          |
| setA-17  | 4           |
| setA-20  | 3           |

Large instances (setA-17, setA-20) ran only 3–4 generations before hitting the time
limit. This means the evolutionary search had almost no opportunity to operate on these
instances — the stagnation limit and generation limit were never reached; the wall-clock
budget was exhausted after initial population evaluation.

**Implication for RP-408:** Even a perfect selection criterion cannot accomplish much
in 3 generations. Before evaluating any algorithmic change on large instances, the
evaluation cost must be addressed. This is a prerequisite for RP-408, not a consequence
of it.

---

## 5. Operator Fingerprints: Not Yet Available

The baseline campaign recorded all 132 accepted improvements with operator tag
`"initial"`. This was caused by two bugs in the evolution loop:

1. Operator tags were built correctly in `next_pop` but discarded when converting to
   the `population` vec — the tag never reached the `RoadefEvaluation`.
2. `gen_crossover_count` and `gen_mutation_count` were re-declared inside the
   `// --- Build next generation ---` block, shadowing the counters that were read by
   `GenerationRecord`.

Both bugs have been fixed in [`adapters/roadef/src/moga_impl.rs`](../../adapters/roadef/src/moga_impl.rs).
The loop now evaluates `next_pop` in-place, stamping each `RoadefEvaluation` with its
operator tag before replacing `evals` for the next iteration.

A corrected campaign must be run before the following questions can be answered:

- Which operator generates most Shoulder improvements?
- Which operator is responsible for Mixed moves?
- Does crossover ever produce Peak improvements?
- Does mutation disproportionately improve the Tail?

## 6. Hypothesis Assessment (Preliminary)

| Hypothesis | Status | Evidence |
|------------|--------|----------|
| H1: Scalar fitness cannot create selection pressure on Peak | **Not established** | Telemetry shows zero Peak moves were accepted, but cannot distinguish generation failure from selection failure |
| H2: Mixed moves indicate multi-zone coupling in the routing graph | **Plausible** | Mixed moves are more common in collapsed-basin instances; topology differences are a candidate explanation |
| H3: Collapsed-basin instances have qualitatively different search dynamics | **Supported** | Mixed move rate 43.9% vs 16.5% is a substantial difference |
| H4: Operator fingerprints differ by zone | **Not yet testable** | Requires corrected campaign |

## 7. Recommended Execution Sequence

1. **Run corrected campaign** (operator tagging now fixed) and re-run
   `scripts/rp410a_analysis.py` to produce operator fingerprint breakdown.
2. **Freeze RP-410A v1.0** once operator fingerprints are verified.
3. **Address evaluation cost** for large instances before RP-408 — 3 generations is
   not a meaningful evolutionary run.
4. **Proceed to RP-408** (native lexicographic evaluation) using the telemetry as the
   evidence base for what the current scalar objective cannot do.
5. **Use RP-407 basin analysis** (`scripts/rp407_basin_analysis.py`) to examine
   whether collapsed-basin instances show diversity collapse before validity collapse.

RP-410A has shifted the discussion from "the solver behaves this way" to "here is

> **Across 132 accepted improvements, 356 generations, and 20 instances, no accepted

This is a precise, falsifiable, empirical statement. It motivates RP-408 without
