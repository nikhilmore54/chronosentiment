## P4 Evidence Pass — Signal Assessment and Authorization Recommendation

**Baseline:** `governance-hardening @ 18cc7dd19`
**Scope:** Inspection of P3 history structures and signal assessment. No code changes.

## Evidence Situation

The P3 history is stored in browser localStorage under two keys:
- `ultracrew_scheduler_decisions` — `SchedulerDecision[]`
- `ultracrew_redistribution_logs` — `Record<string, RedistributionLog>`

This is a development baseline. No accumulated production history exists. The evidence pass therefore assesses the *structure* of what would be recorded after N usage sessions, and determines whether that structure is sufficient to support a recurring signal.

---

## Signal Assessment

### Signal A — Recommendation override with preference characteristics

**Source:** `SchedulerDecision.overrode_recommendation` (boolean)

**What is recorded:** Whether the scheduler overrode the optimizer recommendation. Which alternative was recommended (`recommended_id`) and which was selected (`selected_id`).

**What is NOT recorded:** The metrics (`RosterAlternativeMetrics`) of the recommended and selected alternatives at decision time. Without these, we cannot determine what characteristic drove the override — whether the scheduler preferred lower fairness_penalty, higher coverage, lower cost, or something else.

**Assessment: INCOMPLETE.** The override fact is recorded, but the signal is not interpretable without the metrics. Knowing that the scheduler overrode the recommendation 5 times tells us nothing about what they were optimizing for.

**Gap:** `SchedulerDecision` must be extended to include `recommended_metrics: RosterAlternativeMetrics` and `selected_metrics: RosterAlternativeMetrics` before Signal A can be used.

**Effort to close gap:** Small — add two fields to `SchedulerDecision`, populate them in `SelectDecision.tsx` when recording the decision. No optimizer changes. No Coralys changes.

---

### Signal B — Redistribution reason patterns

**Source:** `ChangeRecord.reason` in `RedistributionLog.changeRecords[]`

**What is recorded:** For every system reassignment during redistribution, the reason string (e.g., `"coverage gap on day 14 Night shift"`). The `assignmentId` (`${staffId}:${dayIdx}`), `previousValue`, `newValue`, and `timestamp` are also recorded.

**What is NOT recorded:** Nothing relevant is missing. The reason, the cell, the shift change, and the session timestamp are all present.

**Assessment: COMPLETE.** If the same coverage gap reason appears across multiple independent redistribution logs (different `operationId`, different `timestamp`), it indicates a recurring coverage weakness that the optimizer is consistently failing to address in its initial schedule.

**Recurring pattern example:**
```
Session 1: ChangeRecord { reason: "coverage gap on day 14 Night shift", ... }
Session 2: ChangeRecord { reason: "coverage gap on day 14 Night shift", ... }
Session 3: ChangeRecord { reason: "coverage gap on day 14 Night shift", ... }
```
This pattern indicates that the optimizer's initial schedule consistently under-assigns Night shift on day 14. The redistribution system is compensating for a recurring optimizer weakness.

**Signal strength:** Strong. The reason string is generated by the redistribution algorithm from the actual coverage deficit, not from scheduler preference. It is objective, not subjective.

---

### Signal C — Scheduler edit count and cell distribution

**Source:** `RedistributionLog.schedulerEditsPreserved` (count), `provenanceMap` (cell-level state)

**What is recorded:** How many cells the scheduler locked before redistribution, and which cells (`scheduler_edit` in `provenanceMap`).

**What is NOT recorded:** What the scheduler changed the cells TO. The `provenanceMap` records the state (`scheduler_edit`) but not the value. The `ChangeRecord` records system changes, not scheduler changes.

**Assessment: LOW INFORMATION.** Knowing that the scheduler locked 3 cells tells us they made 3 manual edits, but not what they changed or why. Without the edit values, this signal cannot drive preference learning.

**Gap:** To make Signal C useful, the scheduler's edit values would need to be captured alongside the provenance state. This is a larger addition than Signal A's gap.

## Recommendation: One-Signal-at-a-Time

**First P4 signal: Signal B — Redistribution reason patterns.**

Signal B is immediately available, complete, and interpretable. It does not require adaptive weights, ML, or constraint learning. It identifies a specific, objective, recurring optimizer weakness.

**Smallest mechanism for Signal B:**

```
After N sessions (proposed: 3):
  Count occurrences of each reason string across all RedistributionLogs
        ↓
  If reason appears ≥ threshold times:
        ↓
  Surface as "recurring coverage pattern" to scheduler
        ↓
  Scheduler decides: accept, adjust manually, or dismiss
```

This is NOT adaptive weights. It is pattern surfacing — presenting the scheduler with evidence of a recurring optimizer weakness. The scheduler retains full authority to act on it or dismiss it.

**What this does NOT do:**
- Does not automatically change optimizer objectives or weights
- Does not modify hard constraints
- Does not change Coralys
- Does not remove scheduler authority
- Does not require ML

**What this requires:**
1. A pattern accumulator that counts `ChangeRecord.reason` occurrences across `RedistributionLog` records in `DecisionRepository`
2. A UI surface (read-only) that displays recurring patterns above the threshold
3. A dismiss/acknowledge mechanism so the scheduler can clear a pattern

**Second P4 signal (after Signal B is implemented and verified):**

Close the Signal A gap: add `recommended_metrics` and `selected_metrics` to `SchedulerDecision`. After N sessions with metrics recorded, assess whether a consistent preference characteristic is observable. Only then consider whether that characteristic should influence future soft objective weights.

---

## Acceptance Gates for Signal B

| Gate | Requirement |
|---|---|
| G-P4-B-1 | Reason string is observable in ≥1 existing `RedistributionLog` |
| G-P4-B-2 | Same reason string appears in ≥3 independent redistribution logs (different `operationId`) |
| G-P4-B-3 | Pattern is not attributable to a single session or a single scheduler |
| G-P4-B-4 | Surfacing the pattern does not modify any optimizer objective, weight, or constraint |
| G-P4-B-5 | Scheduler can dismiss/acknowledge the pattern — it does not persist after dismissal |
| G-P4-B-6 | Behavior without sufficient evidence (< 3 sessions) is identical to current P3 behavior |
| G-P4-B-7 | Hard constraints (HC1, sequence feasibility, eligibility) are not affected |

---

## Conclusion

**P4 implementation authorized for Signal B (redistribution reason pattern surfacing).**

Signal B is complete, interpretable, and requires no optimizer changes. The mechanism is pattern surfacing, not adaptive weights. Scheduler authority is preserved.

Signal A (override preference learning) requires a small additional data capture before it can be used. It is not authorized for implementation until the metrics gap is closed and sufficient history is accumulated.

Signal C (edit distribution) is not authorized — the gap is larger and the signal is lower-value than Signal B.

**P4 implementation sequence:**
1. Implement Signal B pattern accumulator and UI surface
2. Verify against acceptance gates G-P4-B-1 through G-P4-B-7
3. Close Signal A gap (add metrics to `SchedulerDecision`)
4. Accumulate Signal A history
5. Assess Signal A evidence
6. Authorize Signal A mechanism if evidence supports it
