## Core User Journey

The core user journey for UltraCrew follows the Knowledge Evolution Lifecycle adapted for workforce scheduling:

```
Evidence → Hypothesis → Outcome → Pattern → Knowledge
```

In workforce scheduling terms:

| Stage | User Action | Platform Response |
|-------|-------------|------------------|
| Evidence | Provide operational data — crew availability, regulations, disruptions, KPIs | Structured, time-stamped operational evidence record created |
| Hypothesis | Define a scheduling objective and constraints | Roster Strategy created with configurable optimisation profile |
| Outcome | Accept a schedule and operate it | Operational KPIs recorded; learning loop triggered |
| Pattern | Review scheduling cycle outcomes | Workforce behaviour patterns surfaced from evidence and outcomes |
| Knowledge | Validated operational insight added to knowledge graph | Operational Knowledge Graph updated; future schedules benefit |

## Feature Specifications

### Scheduling Workspace

**Purpose:** Structured environment for a single scheduling cycle — from objective definition through schedule generation to outcome recording.

**Core behaviour:**
- Each Scheduling Workspace is linked to a specific scheduling period, crew base, or operational unit
- Operational evidence (crew availability, regulations, disruptions) is captured within the Workspace
- The Workspace persists from schedule creation through operation and outcome recording
- Workspaces accumulate into the Operational Knowledge Graph over time

**Fields:**
| Field | Type | Description |
|-------|------|-------------|
| Scheduling Period | Text | The period being scheduled (e.g. "July 2026 — SunAir BOM base") |
| Operational Context | Text | The operational environment (airport, route network, crew base, constraints) |
| Evidence Items | List | Time-stamped operational evidence items (crew availability, regulations, disruptions) |
| Roster Strategy | Object | The active scheduling hypothesis for this Workspace |
| Roster Versions | List | All roster versions generated in this Workspace |
| Outcome | Object | The recorded operational KPIs when the schedule is completed |
| Created | Date | Date the Workspace was opened |
| Last Updated | Date | Date the Workspace was last updated |
| Status | Enum | Active / Completed / Archived |

---

### Roster Strategy

**Purpose:** Structured hypothesis management — scheduling objective, constraints, optimisation profile, outcome.

**Core behaviour:**
- Each Roster Strategy is a structured hypothesis about how to schedule the workforce for a given period
- Strategies are linked to operational evidence from the Scheduling Workspace
- Optimisation profiles are tracked — each run produces a versioned roster candidate
- Outcomes are recorded when the schedule is operated
- Strategies feed the Workforce Operations Learning Loop

**Fields:**
| Field | Type | Description |
|-------|------|-------------|
| Title | Text | Brief title of the scheduling objective |
| Objective | Text | The core scheduling objective (e.g. "Maximise coverage while minimising overtime") |
| Constraints | List | Hard constraints that must be satisfied (regulatory, contractual, operational) |
| Optimisation Profile | Enum | Coverage / Cost / Fairness / Compliance / Robustness / Balanced |
| Evidence | List | Linked operational evidence items |
| Roster Versions | List | Time-stamped roster candidates generated by the optimisation engine |
| Status | Enum | Active / Accepted / Operated / Archived |
| Outcome | Object | The recorded operational KPIs (when operated) |
| Outcome Date | Date | Date the outcome was recorded |
| Created | Date | Date the strategy was created |
| Last Updated | Date | Date the strategy was last updated |

---

### Optimisation Engine

**Purpose:** Multi-objective genetic algorithm engine that generates optimised roster candidates.

**Core behaviour:**
- The optimisation engine runs a MOGA (Multi-Objective Genetic Algorithm) to generate roster candidates
- Multiple competing objectives are optimised simultaneously: coverage, cost, fairness, compliance, robustness
- The engine maintains an elite archive of the best solutions across generations
- Configurable termination policies: generation limit, time limit, convergence threshold
- Full observability: evolution metrics, processor metrics, convergence tracking per run

**Optimisation objectives:**
| Objective | Description |
|-----------|-------------|
| Coverage | Maximise shift coverage against demand requirements |
| Cost | Minimise overtime, premium pay, and unnecessary assignments |
| Fairness | Distribute workload equitably across the workforce |
| Compliance | Satisfy all hard regulatory and contractual constraints |
| Robustness | Maximise schedule resilience to disruptions |

**Optimisation profiles:**
| Profile | Primary objective | Use case |
|---------|-----------------|----------|
| Coverage | Maximise coverage | High-demand periods; critical operations |
| Cost | Minimise cost | Budget-constrained periods |
| Fairness | Equitable distribution | Long-term workforce satisfaction |
| Compliance | Hard constraint satisfaction | Regulatory audit periods |
| Robustness | Disruption resilience | High-uncertainty periods |
| Balanced | All objectives weighted equally | Standard scheduling cycles |

### Constraint Engine

**Purpose:** Hard constraint enforcement during schedule generation and repair.

**Core behaviour:**
- The constraint engine enforces hard constraints during optimisation — not as post-hoc validation
- Constraints are domain-configurable: regulatory (FDP, duty time, minimum rest), contractual (hours limits, days off), operational (qualification matching, base return)
- Constraint violations trigger automatic repair heuristics before the solution is evaluated
- Constraint audit reports are generated for every accepted schedule

**Constraint categories:**
| Category | Examples |
|----------|---------|
| Regulatory | Flight Duty Period (FDP) limits, minimum rest periods, duty time limits |
| Contractual | Maximum weekly hours, minimum days off, shift type restrictions |
| Operational | Qualification matching, base return requirements, coverage minimums |
| Fairness | Maximum consecutive shifts, equitable weekend distribution |

### Disruption Recovery

**Purpose:** Real-time re-optimisation when operational plans change.

**Core behaviour:**
- When a disruption occurs (crew unavailability, flight cancellation, operational change), the disruption is recorded as an evidence item in the Scheduling Workspace
- The optimisation engine re-runs with the disruption as a hard constraint
- Recovery options are ranked by impact on the remaining schedule
- The disruption and recovery are recorded in the Scheduling Timeline
- Disruption patterns accumulate in the Operational Knowledge Graph

**Disruption types:**
| Type | Description |
|------|-------------|
| Crew unavailability | Crew member becomes unavailable (illness, personal, regulatory) |
| Flight disruption | Flight delay, cancellation, or diversion |
| Operational change | Route change, aircraft swap, base change |
| Regulatory change | New regulatory requirement affecting active schedules |

---

### Scheduling Timeline

**Purpose:** Chronological view of all scheduling decisions and operational events.

**Core behaviour:**
- The Scheduling Timeline is a chronological feed of all evidence items, roster versions, disruptions, and outcomes for a Scheduling Workspace
- Items are filterable by type, date range, and crew member
- The timeline provides a complete audit trail of every scheduling decision
- Timeline items link back to their source evidence or roster version

**Timeline item types:**
| Type | Description |
|------|-------------|
| Evidence Captured | New operational evidence added to the Workspace |
| Roster Generated | A new roster candidate was generated by the optimisation engine |
| Roster Accepted | A roster candidate was accepted for operation |
| Disruption Recorded | An operational disruption was recorded |
| Recovery Generated | A disruption recovery option was generated |
| Outcome Recorded | Operational KPIs were recorded for the completed schedule |
| Pattern Identified | A workforce behaviour pattern was identified |

---

### Workforce Operations Learning Loop

**Purpose:** Post-cycle review process — what worked, what didn't, what to change.

**Core behaviour:**
- The Learning Loop is triggered at the end of each scheduling cycle (or manually)
- It surfaces completed schedules, operational KPIs, and disruption patterns from the cycle
- The scheduler reviews each completed cycle: what drove the outcomes, what would they do differently
- Patterns are identified across multiple cycles and crew bases
- Validated insights are added to the Operational Knowledge Graph
- The Learning Loop produces a cycle review report

**Learning Loop stages:**
| Stage | Description |
|-------|-------------|
| Review | Surface completed schedules and KPIs from the cycle |
| Reflect | Scheduler reflects on outcomes — what drove them, what they'd do differently |
| Pattern | Patterns identified across multiple cycles and crew bases |
| Insight | Validated insights added to the Operational Knowledge Graph |
| Report | Cycle review report generated |

---

### Operational Knowledge Graph

**Purpose:** Accumulated operational knowledge — disruption patterns, crew behaviour patterns, scheduling insights.

**Core behaviour:**
- The Operational Knowledge Graph is the persistent, structured knowledge asset for the organisation
- It accumulates entities (crew members, routes, bases, disruption types) and relationships (disruption patterns, recovery patterns, scheduling outcomes)
- Patterns are surfaced from the graph by the Continuous Learning Engine
- The graph evolves over time as new scheduling cycles, disruptions, and outcomes are added
- The graph is queryable — schedulers can explore operational patterns directly

**Entity types:**
| Type | Description |
|------|-------------|
| Crew Member | A specific crew member with qualifications and history |
| Route | A specific route or flight leg |
| Base | A crew base or operational hub |
| Disruption Type | A category of operational disruption |
| Roster Strategy | A scheduling hypothesis |
| Evidence | A structured operational evidence item |
| Outcome | A recorded set of operational KPIs |
| Pattern | A recurring structure in disruptions, decisions, or outcomes |
| Knowledge | A validated, durable operational insight |

## User Experience Principles

1. **Schedules first** — the primary output is always a schedule. The knowledge layer is the engine behind it, not the interface.
2. **Explainability by default** — every schedule recommendation should be explainable to the operations manager who acts on it. "Why was this crew member assigned here?" must always have an answer.
3. **Disruption is expected** — the product is designed for operational reality, not ideal conditions. Disruption recovery is a first-class workflow, not an edge case.
4. **Knowledge compounds** — every scheduling cycle should make the next one better. The scheduler should feel the compounding effect over time.
5. **Compliance is built in** — regulatory and contractual constraints are enforced during generation, not checked after the fact.
