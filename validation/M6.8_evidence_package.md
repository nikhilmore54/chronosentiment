## 5. Reproducibility Guide

All qualification tests are standard Rust integration tests. They require no external data, network access, or environment configuration beyond a working Rust toolchain.

### Prerequisites

- Rust toolchain (see Section 6 for version)
- Repository cloned at branch `governance-hardening`

### Commands

Run all qualification tests:

```sh
cargo test --package coralys-scheduling
```

Run individual milestone tests:

```sh
# M6.2 — Functional correctness
cargo test --package coralys-scheduling --test scenario_validation -- --nocapture

# M6.3 — Solution quality
cargo test --package coralys-scheduling --test solution_quality -- --nocapture

# M6.4 — Scalability
cargo test --package coralys-scheduling --test scalability -- --nocapture

# M6.5 — Robustness
cargo test --package coralys-scheduling --test robustness -- --nocapture

# M6.6 — Benchmark
cargo test --package coralys-scheduling --test benchmark -- --nocapture
```

All tests print structured output to stdout when run with `--nocapture`. The output includes baseline scores, optimized scores, improvement percentages, evaluation counts, and acceptance ratios, matching the values reported in the evidence documents.

### Expected output

Each test suite should report:

| Test suite | Expected result |
|------------|----------------|
| `scenario_validation` | 11 passed, 0 failed |
| `solution_quality` | 1 passed, 0 failed |
| `scalability` | 1 passed, 0 failed |
| `robustness` | 3 passed, 0 failed |
| `benchmark` | 4 passed, 0 failed |

| Random seed | None — all fixtures are deterministic; no random number generation |
| Parallelism | Tests may run in parallel (Rust default); each test is independent |

**Note on determinism:** All qualification fixtures are fully deterministic. The optimizer uses no random number generation. Candidate moves are generated deterministically from the roster contents; however, if standard `HashMap` iteration is used internally, traversal order is not guaranteed across platforms or Rust implementations. Qualification results were produced using the toolchain listed above. The final objective score and all correctness invariants are stable across runs on the same platform and toolchain version. This is documented in the M6.3 evidence document.

## 8. Qualification Scope Summary

The optimizer is qualified within the following envelope (full definition in M6.7, Section 11):

- Legal starting roster (all rotations ≥ 2 pairings, chronological ordering)
- `WorkloadBalanceObjective` (leg-count variance), single-objective
- Steepest-descent local search, feasible-state only
- Up to 16 rotations / 64 pairings
- Synthetic scheduling instances

The following are explicitly outside the qualified envelope: infeasible-state repair, multi-objective optimisation at scale, real airline scheduling datasets, hardware-dependent runtime guarantees.
