## Experimental Design

### Fixture

| Property | Value |
|----------|-------|
| Crew rotations | 4 |
| Pairings | 12 (LHR-CDG-LHR, non-overlapping) |
| Pairing duration | 5 h (2h out + 1h ground + 2h return) |
| Slot spacing | 6 h |
| Time range | 2026-07-01 00:00Z to 2026-07-01 66:00Z |

### Baseline (deterministic, reproducible)

Round-robin assignment with deliberate imbalance:

```
ROT1 (C1): P06, P07, P08, P09, P10, P11  — 6 pairings (dep_h 36..66)
ROT2 (C2): P00, P01                       — 2 pairings (dep_h 0..6)
ROT3 (C3): P02, P03                       — 2 pairings (dep_h 12..18)
ROT4 (C4): P04, P05                       — 2 pairings (dep_h 24..30)
```

**Fixture design note:** The heavy rotation holds the LATEST pairings and the light
rotations hold the EARLIEST pairings. This ensures that `relocate_pairing` moves
(which append to the end of the destination rotation) always satisfy the
`Rotation::new` chronological ordering constraint.

### Optimized Pipeline (frozen)

```
Baseline roster
      │
      ▼
LocalSearch (200 iterations, WorkloadBalanceObjective, no legality constraints)
      │
      ▼
Optimized roster
```

### Objective

`WorkloadBalanceObjective` — variance of total flight-leg counts across rotations.
Lower is better. A perfectly balanced roster scores 0.0.

## Engineering Findings

### Finding 1 — Rotation chronological ordering constraint

`Rotation::new` validates that pairings are in chronological order:
`pairings[i].start() >= pairings[i-1].end()`. The `relocate_pairing` neighborhood
move appends the moved pairing to the **end** of the destination rotation. Therefore,
the moved pairing must have a start time ≥ the last pairing's end time in the
destination rotation.

**Fixture design rule:** The heavy rotation must hold the LATEST pairings; light
rotations must hold the EARLIEST pairings. This guarantees that all relocate moves
satisfy the ordering constraint.

### Finding 2 — Roster stores rotations in a HashMap

`Roster` stores rotations in `HashMap<CrewId, Rotation>`. Iteration order is
non-deterministic. The `LocalSearch` collects rotations into a `Vec` and indexes
them by position. If a light rotation (1 pairing) appears at index 0, `relocate_pairing`
returns `None` (cannot relocate the only pairing). All rotations must have ≥ 2 pairings
to guarantee that relocate moves succeed regardless of HashMap iteration order.

**Fixture design rule:** All rotations must have ≥ 2 pairings in the baseline.
